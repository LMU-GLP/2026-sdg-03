# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is not a software project — there is no build, lint, or test tooling. It is a
**research wiki** built during a live workshop (LMU GLP 2026) for SDG 03 (Good Health
and Well-being). The team's challenge: "How might we support young people's mental
health through a simple product, service, or community program?" (region: Los Angeles,
South Korea, or elsewhere, to be chosen by the team).

The repo starts as just this `README.md` and `CLAUDE.md`. Over the course of the
workshop, a team of students uses Claude Code to grow it into three layers:

- `sources/` — one markdown file per raw source a student researched
- `wiki/` — synthesized pages Claude writes by ingesting everything in `sources/`
- `wiki/problem-statement.md` — the team's final, defensible problem statement

If those directories don't exist yet, the workshop is still in its early steps —
create them as the workflow below calls for it, don't treat their absence as an error.

## Workflow (follow the README's step order)

The full step-by-step script for running the workshop lives in `README.md` — read it
before improvising. The high-level shape:

1. **Interview, once, with one driver.** At the start, interview the team one question
   at a time (multiple-choice where possible) about their challenge, candidate regions,
   and research needs before writing anything. Merge this setup to `main` immediately
   so teammates' sessions don't fork from an empty repo.
2. **Parallel research, one source per person.** Each teammate claims a distinct source
   (a UN target page, a dataset, a news story per region, an existing product/program)
   and asks Claude to research just that one. See "Source file conventions" below.
   Do not touch `wiki/` during this step.
3. **Commit and push to a personal draft branch**, then open a PR — never push
   directly to `main`. See "Git workflow" below.
4. **Synthesis, once, with one driver.** Ingest everything under `sources/` and update
   `wiki/` accordingly.
5. **Problem statement.** Draft `wiki/problem-statement.md` by interviewing the team
   one question at a time, grounded in what the wiki now contains. Every claim in it
   needs a citation back to a source; treat uncited claims as placeholders, not fact.

## Source file conventions (`sources/`)

Each file is a single researched source. Required content, per the README:
- Page title
- Source URL
- The date it was captured (use today's date, not the source's publish date)
- Key facts and figures, with short direct quotes (exact numbers, not paraphrases)
- A two-sentence summary

Do not paste whole articles into the repo — a judge wants the figure and the citation,
not a mirror of the page. Never edit `index.md` or wiki pages while doing source
research; that happens only during the synthesis step.

## Wiki conventions (`wiki/`)

Wiki pages are derived, not hand-authored from scratch — they should be generated by
ingesting `sources/` (per the karpathy LLM-wiki approach linked in the README) rather
than written independently of the source material. Every factual claim in a wiki page,
and especially in `wiki/problem-statement.md`, must trace back to a citation in
`sources/`. When ingesting sources to update the wiki, look for contradictions and gaps
across sources rather than silently picking one.

## Git workflow

- Everyone works on their **own draft branch**; nobody pushes straight to `main`.
- Publish by opening a PR from the draft branch and merging it — through the workshop,
  the team plays the role of PR reviewer.
- Merge conflicts are expected when multiple people finish around the same time;
  resolve by merging `main` into the draft branch, not by discarding either side.
- The interview/setup step (step 1) and the synthesis step (step 4) must be merged to
  `main` promptly after each runs, since every other step assumes teammates are
  branching from an up-to-date `main`.
